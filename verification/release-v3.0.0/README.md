# UI Test Actions v3.0.0 release acceptance

All rows in this report use the published Action commit `a56957b05ce72ed15c0c35daad572a2add0d173e`. The independent consumer called it by full SHA. Its workflows fetched pinned upstream applications or selected fixture files through a separate checkout. The Action and controller code used the same revision. The release uses the same commit for every platform and transport. ## Scope and recovery observations

- The first ARM64 iOS hour run failed before publication when `simctl list devices booted` timed out. The independent workflow added an explicit check that the Simulator had a responsive SpringBoard. The retry used the same Action SHA. During the separate iOS cancellation proof, a lost batch response reported an uncertain outcome. The external agent reconnected, found the field focused and empty, issued only the remaining actions, and verified the actual change before cancelling. [Startup failure](https://github.com/ui-test-actions/ui-test-actions-consumer-acceptance/actions/runs/44849579761) · [iOS cancellation recovery](cancellation/ios/)
- The browser harness resumed its saved history after the SDK had already turned the Windows fixture green. The resumed capture detected the current green window and completed the tree, recording, and cross-device UI checks. The Appium Android harness used Android's native uppercase button label and a larger two-finger spread after inspecting the first reachable screen. [Browser](browser/) · [Android native gesture](mobile-adapters/appium-android/)
- The first fault test measured native delay while the observation harness moved away from the receiver timeline. The native AXe retry timed out capturing the P2pKit framebuffer on that hosted image. A fresh visible-backend attempt stopped before Android boot because Ubuntu could not locate its packages. The consumer added a bounded package-index refresh and retry. The final retry used Android to send both fault-test payloads and kept iOS in its receiver role. It observed an app disconnect and a fresh delivery after re-pairing. [Early visible trial](https://github.com/ui-test-actions/ui-test-actions-consumer-acceptance/actions/runs/44851212389) · [AXe capture failure](https://github.com/ui-test-actions/ui-test-actions-consumer-acceptance/actions/runs/44853371821) · [Package-index failure](https://github.com/ui-test-actions/ui-test-actions-consumer-acceptance/actions/runs/44854334430) · [Visible trial](https://github.com/ui-test-actions/ui-test-actions-consumer-acceptance/actions/runs/44854676658) · [Final observed retry](https://github.com/ui-test-actions/ui-test-actions-consumer-acceptance/actions/runs/44856486177)
- Verified Apple configurations use the workflow's pinned ARM64 runner and backend combinations. Other Xcode, Simulator, or Appium combinations require separate qualification. The hosted LAN test covers IPv4 app discovery and TCP on the isolated emulator pair. Physical radio behavior requires compatible physical devices. Arabic hardware composition requires a physical device with an Arabic-layout keyboard or the OS Arabic input layout. Tailscale qualification needs an isolated tailnet and an enrollment identity. Interactive Cloudflare browser sign-in needs an identity provider or a test identity admitted by a human Access policy. The separate Service Auth path was verified end to end. [External scope and reproduction](https://github.com/ui-test-actions/ui-test-actions/blob/a56957b05ce72ed15c0c35daad572a2add0d173e/docs/external-acceptance.md)
- Cloudflare describes Quick Tunnels as a development and testing service without an uptime guarantee. The hosted test documents the exact runner and toolchain used. The tested dedicated Named and existing private-route configurations provide alternatives with their own prerequisites. [Connection settings and examples](https://github.com/ui-test-actions/ui-test-actions/blob/a56957b05ce72ed15c0c35daad572a2add0d173e/docs/transports.md) · [Quick Tunnel provider limits](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
